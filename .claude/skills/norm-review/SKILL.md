# norm-review — 規範の棚卸し

規範は足すのが簡単で、消すのは難しい。既にあるというだけで残り、新しいやり方を妨げることもある。
この Skill は週に 1 回、規範を「あるから残す」ではなく証拠で審理する。逆に、user が何もしていない
のに時間が経っただけで規範が減っていくこともさせない。

## 守ること（審理の全工程で）

1. **消す・下ろすにも証拠が要る。** 根拠にできるのは観測された事実だけ: 誤検知（hook_replay・発火の逐語）、
   user が規範に逆らって正しかった場面、規範同士の食い違い、規範と実物（ファイル・コード）の食い違い、同じ誤りが道具・順序の側で既に起きなくなった事実。
   **発火 0・読まれない・経過日数だけでは「保留」にする**（常に読み込まれる規範は、効いているほど失敗が記録されない）。
   `check` がこれを機械で止める。
2. **1 週の「消す」「下ろす」は上限まで**（config の `max_removals`、既定 3）。超える分は証拠の弱い方から保留にする。
3. **禁止より仕組み。** 「〜するな」で防いでいる誤りは、`.claude/rules-ondemand/skill-revision.md` の 2 の手段
   （検査を前に出す・出す側を直す・検査で止める・手順の組み方を変える）で起きなくできないかを先に問う。
   置き換えるときは、置き換え先の仕組みを変更案に書く（消すだけにしない）。
4. **無人の審理では規範のファイルを書き換えない。** 変更案は判定ファイルに差分で書き、反映は user がいる会話で行う
   （自己改変は無人では拒否され、抜け道で回避しない）。
5. **CLAUDE.local.md の「絶対命令」と「衝突時の優先順位」の節** は審理してよいが、消す・下ろす・置き換えるの
   変更案は「相談:」で始め、反映は user と会話で決める。
6. **発展の阻害も罪状に数える。** 規範のせいで回り道した・user が規範を外させた・規範が良い手を禁じていた記録は、
   誤りと同じ重さで扱う。

## 週次の審理（TODO の「規範の棚卸し（週次）」ストーリー）

ストーリーの 範囲 に、審理一覧（`<state_dir>/lists/<日付>.txt`）と判定ファイルのパスが書いてある。
`<state_dir>` は repo ルートの `.local/norm-review/`（config は同じ所の `config.json`）。

1. **持ち越しを読む。** `<state_dir>/verdicts/*.md` の `状態: 提案中` を数え、判定ファイルの冒頭に「持ち越し N 件」として
   一覧の名前だけ書く。同じ物を今週もう一度起訴しない（新しい証拠が出たときだけ、その証拠を足す）。
2. **証拠を集める**（決まった手順の道具だけ。出力は `<state_dir>/evidence/<日付>/` に保存）:
   - `python3 heaven/tools/telemetry_report.py --days 140`（発火・未配線・未計装）
   - `python3 heaven/tools/rule_efficacy_report.py --all`（発火 ÷ 呼び出しの週ごとの率）
   - `python3 heaven/tools/observe_mode_report.py --days 14`（観察モードのまま期限を過ぎた hook）
   - `python3 heaven/tools/promotion_layer_report.py --days 30`（常時読み込みの節の効きの記録）
   - 一覧にある Bash の PreToolUse hook ごとに `python3 heaven/tools/hook_replay.py --hook <名前> --days 30 --limit 2000`（誤検知の数）
   道具が無い・失敗した物は「取れなかった」と判定ファイルに書き、その物の証拠は無いものとして扱う。
3. **検察役を起動する** — Agent ツール `subagent_type: root-cause-auditor`・`model: opus`。一覧が 40 件を超えるなら
   2 つに分けて 1 つのメッセージで並べて起動する。指示文は下の「検察役への指示」を、一覧と証拠のパスを埋めて渡す。
4. **弁護役を起動する** — 起訴された物だけを渡す。Agent ツール `subagent_type: norm-defender`・`model: opus`。
   指示文は下の「弁護役への指示」。起訴が 0 件なら起動しない。
5. **裁定する（親＝Fable 自身）。** 起訴された物ごとに、両方の論を読み、**論の拠り所になっている逐語・行を自分で開いて**
   確かめてから判定する（係の「誤りだ」「問題ない」は結論であって証拠ではない）。判定は
   `残す / 置き換える / まとめる / 下ろす / 消す / 保留` のどれか。起訴されなかった物は `残す`・`起訴: なし`。
6. **判定ファイルを書く**（形は下）。`python3 .claude/skills/norm-review/scripts/norm_review.py check <判定ファイル> --list <審理一覧> --max-removals <N>`
   が OK になるまで直す。
7. **報告**（todo-loop の報告 JSON）の「まとめ」に、判定の件数（種類ごと）・持ち越しの件数・
   「反映は会話で『棚卸しの反映』と言えば一覧が出る」を書く。

### 判定ファイルの形

```
# 規範の審理 <日付>（区画 k/n）
持ち越し: N 件（<名前>, ...）
取れなかった証拠: <道具名と理由> / なし

### <一覧の名前（1 列目そのまま）>
- 判定: 消す
- 起訴: <罪状の種類> — <要旨 1 行>
- 観測: <逐語の引用と出どころ（ファイル:行 / 会話記録の sid と時刻 / 道具の出力の行）>
- 弁護: <要旨 1 行>
- 理由: <裁定の理由 1〜3 行。弁護のどこが証拠で崩れたか>
- 変更案: <差分、または置き換え先の仕組みと触るファイル>
- 状態: 提案中
```

`残す` と `保留` は 判定・起訴・（あれば）理由 だけでよい。`状態` は `提案中 / 反映済み / 却下 / 不要`。

### 検察役への指示（root-cause-auditor に渡す）

> あなたは規範の審理の検察役です。下の審理一覧の各規範について、残す理由ではなく、変える理由を探してください。
> 罪状は 6 種類: (1) 誤り — 規範が正しくない判断を強いた（誤検知・user が上書きして user が正しかった）
> (2) 禁止で済ませている — 順序・道具・検査に置き換えれば起きなくなる誤りを「するな」で防いでいる
> (3) 重複・食い違い — 同じ趣旨の別の規範がある、または規範同士が逆を言う
> (4) 常時読み込みの過剰 — 毎ターン読む層にあるが、特定の場面でしか要らない
> (5) 発展の阻害 — 規範のせいで回り道した・良い手を禁じていた記録がある
> (6) 実物との食い違い — 規範が書いている道具名・パス・hook の挙動・設定値が、今のファイル・コードと合わない
> （規範に出てくるパスは `ls`、hook・道具は該当コードを読んで確かめる）。
> 証拠に使ってよいのは観測だけです: 証拠フォルダの道具の出力、会話記録（`~/.claude/projects/*/*.jsonl` を
> 規範の名前・hook のメッセージの語で grep し、その直後の user の発話を読む）、規範のファイル本文、
> memory（`heaven/memory/`）・経緯ファイル。**発火 0・読まれないことだけでは起訴しないでください**（それは罪状ではない）。
> 証拠が見つからない規範は「起訴なし」と 1 行で返してください。起訴する物には、罪状・逐語の引用・出どころ
> （ファイル:行 / sid と時刻）・どう変えるべきかの案を返してください。判定はしないでください（裁定は別の役）。
> 何も書き換えないでください。返答は日本語で、ファイルパス・コード識別子・固有名詞以外の英語を使わないでください。
> 審理一覧: <パス>（担当: <範囲>）／ 証拠フォルダ: <パス> ／ 持ち越し中で起訴しない物: <名前の列>

### 弁護役への指示（norm-defender に渡す）

> 下の起訴状の各規範について、弁護役として残す側の論を作ってください。<起訴状をそのまま貼る>
> 証拠フォルダ: <パス>

## 反映（user がいる会話で）

「棚卸しの反映」「棚卸しの承認」と言われたら:

1. `<state_dir>/verdicts/*.md` の `状態: 提案中` を全部、判定ファイルごとに 1 行ずつ（名前・判定・変更案の要旨）出す。
   「相談:」で始まる物は分けて出す。
2. user が決めた物を、この会話で反映する（Edit・ファイルの移動・settings の配線の削除）。反映した物ごとに、
   関係する試験（`python3 -m pytest .claude/hooks/tests -q` 等）を走らせ、判定ファイルの `状態` を `反映済み` に書き換える。
   user が退けた物は `却下`、もう当たらない物は `不要`。
3. user が「推奨で」と言ったら、`消す`・`下ろす`・`置き換える`・`まとめる` を全部反映し、「相談:」の物だけ残して聞く。

## status

`.local/norm-review/gate.log` の末尾 5 行、`state.json` の `last_enqueued`・`last_story`・`next_slice`、
持ち越し（提案中）の件数を出す。

## 週次の起動（仕組み）

`norm_review.py gate --config .local/norm-review/config.json` を launchd が毎朝 1 回呼ぶ。積むのは次の 4 つを
全部満たした日だけ:
前回の積み込みから `interval_days` 以上経った ／ 前回の審理が `done` ／ 前回以降の人の発話が `min_utterances` 件以上・
`min_days` 日以上（無人の回・下請けへの指示は数えない）／ todo-loop が実行中でない。
人の活動が無い週は積まず、区画も進めない（時間が経っただけでは何も起きない）。審理一覧には、区画の巡回分に加えて、
**前回の積み込み以降に新しく足された・書き換わった規範を必ず入れる**（足した直後に一度は審理を通す）。
積んだストーリーは todo-loop が Fable で実行する。

失敗したとき: 審理の回が利用上限で止まったら、todo-loop は失敗に数えず翌朝の回で続きから行う。関門が例外で
落ちたら `gate.log` に `error` を書き、config の `notify`（本文を標準入力で受けるコマンド）で知らせる。前回の審理が
`done` にならないまま `stall_days`（既定 14）を超えたら、1 回だけ同じ先に知らせる。
