# 根拠の範囲 — user の発言も出典も、逐語の範囲だけを使い、成果物には札と原文を付ける

<important if="user の発言・申告・観測や、外部の資料（一次ソース・記事・まとめ・検索の要約）を、判断・結論・成果物（ページ・ガイド・docs・報告・記録欄）の根拠に使おうとしている、または成果物を渡そうとしている">

「user の観測は自分の推定より上位」「一次ソースに書いてある」という決まりは、言葉を広げて読んだ主張にまで
上位の格を与えてしまう。広げた主張を user や出典の名前で成果物に載せると、相手が言っていないことを言ったように見える。
記事やまとめの記述を、一次ソースで確かめないまま事実として書くのも同じ型の誤り。

1. **正とするのは、発言・出典の逐語の範囲（主語・対象・数・条件）だけ。** それより広い主張（一部 → 全部、
   ある物 → 同じ種類の全部、一度 → いつも、条件付き → 無条件）は、別の根拠で確かめるまで書かない。
   書く前に、元の文を逐語で引いて、自分の主張と主語・対象・数を 1 語ずつ照らす。
2. **成果物の根拠欄・出典・訂正の経緯に、user の発言を載せない。** user の観測を受けたら、同じターンで
   一次ソースを探して、それを根拠に書く。見つからなければ「実機で確認（日付）」と書き、user の名前と発言は出さない。
3. **二次資料（記事・まとめ・検索の要約）の記述は「記事の記述」と書く。** 一次ソースで確かめた物だけを、
   一次ソースの名前の札で書く。記事の名前が引けない物・特定できない物を、名前の近い別の物に置き換えない。
4. **判断の根拠になる文は、要約と並べて出典の原文を引く。** 要約が出典の範囲を越えたら、読む人がその場で気づける。
   札の検査（下の 5）は札の有無しか見ないので、範囲の誤りはこれでしか防げない。
5. **渡す前に 2 つの検査を通す**:
   - `python3 heaven/tools/user_quote_check.py <成果物>` — このセッションの user の発言と 14 文字以上一致する部分と、
     user を主語・出典にした書き方（「user「」「user の実機観測」等）で止まる。
   - `python3 heaven/tools/source_audit.py <成果物> [--tokens <プロジェクトの札の語>]` — 仕組み・数値・確定・義務を
     言い切る文に、出典・確度の札（出典名・推測・記事・未確認 等）が無いと止まる。
6. 例外: 記録欄（TODO の決定欄・spec・handoff）に user の判断を書くときは、逐語で引用してよい
   （無人のセッションが読む欄では、言い換えた帰属が確認の機会なしにそのまま実装になるため、逐語が安全）。
   その場合も言い換えず、自分の解釈は「解釈（user 未確認）」として別の行に分ける。

</important>
